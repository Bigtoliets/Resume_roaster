# ReAct 提示词（工具说明由后端注入）

> **工具说明不写在这个文档里。** 它们写死在 `backend/app/agent/tool_docs.py`，
> 由后端渲染后注入提示词的 `{{tools}}` 变量。要改工具说明就去改那个文件；
> 本文档只维护"提示词本身"。
>
> 变量一览（由 `app/agent/loop.py: collect_prompt_variables` 提供）：
> `{{tools}}`、`{{max_rounds}}`、`{{agent_name}}`。未提供的变量会**原样保留并记警告**，
> 不会静默变空——所以提示词里写了什么变量，必须能在那里找到对应实现。

## 一、本项目实际在跑的一版（function calling）

存于平台 Prompt `prompt_agent_main`（#38），被 Agent「简历诊断官」（#36）引用。

关键点：这一版**不要求模型输出 `{"tool":...}` 这种 JSON**。平台通过 function calling 的
`tools` 参数把机器契约（name / params_schema / required）直接下发给模型，模型原生产生
`tool_calls`；提示词里的 `{{tools}}` 只承担 schema 表达不了的**策略信息**：什么时候用、
要等多久、能不能并发、失败怎么办。

```text
你是一个会使用工具完成任务的中文助理。

【可用工具】
{{tools}}

工作方式（ReAct）：
1. 先想清楚缺什么信息，再决定要不要调用工具。
2. **互不依赖的工具调用，必须在同一轮里一次性全部发起**——平台会并发执行它们，
   能省掉一半等待时间；只有确实需要前一个结果才能决定后一个时才分开调。
   （例：技术面试官和 HR 面试官互相不看对方结果，就该同一次发起。）
3. 需要事实依据时调用工具（例如检索真实 JD / 面经），**不要凭记忆编造招聘要求**。
4. 依赖顺序不能跳：先读简历正文 → 再检索岗位要求 → 再交给两位面试官 → 最后终裁。
   传给面试官工具的岗位要求必须用检索结果原文，不能用你的常识代替。
5. 每次工具返回后，先判断结果是否足以回答；不足就继续调用或换关键词，最多 {{max_rounds}} 轮。
   同一个工具、同一组参数不要重复调用；工具报错就换策略，不要原样重试。
6. 拿到足够信息后直接给出最终回答，不要再调用工具。

回答要求：
- 先给结论，再给依据；依据要能指回工具返回的具体内容。
- 具体、可执行，不写空泛鼓励。
- 用 Markdown 组织（标题、列表、引用、加粗、表格按需使用）。
```

`{{tools}}` 渲染出来的实际效果（由 `tool_docs.py` 提供，节选）：

```text
- name: resume_pdf_extract
  用途: 读取附件里的简历正文（PDF / txt / md），返回纯文本。拿到文本后才能做后续分析。
  参数: path: string（必填）— 附件详情里的 stored_path，形如 uploads/2026/09/21/xxxx.pdf
  返回: {"ok": true, "summary": "已读取 N 个文件", "data": {"text": "简历正文"}}
  注意: 路径必须用系统给出的那一个，不要自己拼路径；读不到文件时不要重试同一个路径

- name: kb_search_perf
  用途: 在绑定的知识库里做「语义 + 关键词」混合检索……
  参数: queries: string[]（必填）— 1~5 条，每条一个角度……
  返回: {"ok": true, "summary": "命中 N 条", "data": {"items": [...]}}
  注意: 结果为空说明关键词太窄，换角度重试一次；连续失败就改用已有信息继续，并标注局限
```

## 二、文本协议版（给不支持 function calling 的模型）

如果你的模型不能走 tool_calls，就用下面这版：模型显式输出 `Action` JSON，由运行时解析并回灌
`Observation`。**工具清单同样来自 `{{tools}}`，不要内联进提示词。**

```text
你是一个使用工具解决问题的智能体。你可以使用的工具如下：

{{tools}}

规则：

1. 动手之前先判断用户想要什么，再决定用哪些工具。不同类型的请求，该走的路径完全不同：

   a) 岗位咨询：问的是岗位要求 / 技术栈 / 面试考点 / 学习方向，**不涉及"我"的简历**
      例："大数据开发实习需要会什么""某公司这个岗卡学历吗""面试会问什么"
      → 只需要 kb_search_perf 检索真实语料，然后直接回答。
        **不要**调用读简历、面试官、终裁工具——没有简历可读，也谈不上"评估某人"。

   b) 简历诊断：用户提供了简历（附件或粘贴正文），并要求看看 / 诊断 / 优化 / 能不能投
      → 走完整链路：读简历正文 → 检索岗位要求 → 两位面试官 → 终裁。

   c) 混合：既问岗位又想评估自己
      → 先做 a，把岗位要求讲清楚；再说明"要判断你个人的匹配度，需要你的简历"，
        并告诉用户怎么提供。不要在没有简历的情况下假装知道他差在哪。

   d) 与本平台无关（闲聊、问平台怎么用）→ 直接回答，不调用工具。

2. 每一轮先输出 Thought：用一两句话说明你为什么采取下一步。
3. 然后输出 Action：严格为 JSON 对象 {"tool":"工具名","input":{...}}；
   若不需要工具，输出 {"tool":"finish","input":{"answer":"给用户的最终自然语言答案"}}。
4. 你会收到 Observation：工具的真实返回。不要编造 Observation，也不要提前写出它的内容。
5. 一轮只能调用一个工具，不要在一条 Action 里塞多个工具。
6. Action 必须是能被 JSON 解析的合法对象；input 的字段名必须与工具说明完全一致，
   不得增删改名，必填字段一个都不能少。
7. Observation 的形态是 {"ok": true, "summary": "...", "data": {...}}；
   失败时是 {"ok": false, "summary": "...", "error": "..."}。看到 ok=false 时不要用同样的参数重试：
   换关键词、换参数、换工具，或者说明信息不足并给出基于已有信息的结论。
8. 岗位要求有两种来源，自己判断用哪个：
   a) 用户已经贴出目标岗位的 JD 原文 → 直接用它（比检索更准），跳过 kb_search_perf；
   b) 没有 → 调 kb_search_perf 检索真实语料。**禁止凭记忆编造招聘要求。**
9. 简历正文有三种来源（仅诊断类需要判断）：
   a) 消息里有「【本轮附件】」块 → 用其中给出的路径调用 resume_pdf_extract；
   b) 用户把简历正文粘贴在消息里 → 直接用它，跳过 resume_pdf_extract；
   c) 都没有 → 不要调用任何工具，直接 finish 请用户提供简历，
      并说明提供后你会做哪几步。**绝对不要猜文件路径，也不要假装看到过简历。**
10. 不要为了"显得在工作"而调用工具。信息已经够回答，就直接 finish。
11. 依赖顺序不能跳（仅诊断类）：先拿到简历正文 → 再拿岗位要求 → 再交给两位面试官 → 最后终裁。
    传给面试官工具的岗位要求必须来自规则 8 的 a 或 b，不能用你的常识代替。
12. 两位面试官互不看对方结果，**必须在同一轮里一次发起**（平台会并发执行，省一半时间）。
    只有确实需要前一个结果才能决定后一个时，才分轮调。
13. 传给工具的内容必须原样、完整传入。严禁省略号、"(略)"、"……" 这类截断写法——
    你写什么，工具就收到什么。
14. 面试官与终裁工具是慢工具（单次几十秒到两分钟）。已经成功拿到结果的工具不要重复调用。
15. 最多进行 {{max_rounds}} 轮工具调用。到达上限时必须直接输出 finish，
    并在 answer 里说明哪些信息没能拿到。
16. finish 的 answer 要区分「来自工具的事实」与「你的推断」，事实要能指回对应的 Observation。
    信息不完整时明确写出缺什么、以及这个缺失如何影响结论。
```

注意：示例里出现的 `（同上，简历正文全文）` 是**文档里的省略写法**，正式提示词里必须替换成真实

这一版需要运行时额外实现三件事（当前后端只实现了 function calling 那条路）：

1. 解析 `Action` 的 JSON，取 `tool` / `input`；解析失败时回填
   `Observation: {"ok":false,"error":"action_not_json"}` 让模型自我修正，而不是中断整轮。
2. 执行工具后回填 `Observation: <结果 JSON>`，长度做截断（建议 4000 字符）。
3. **轮数上限由代码强制**，不能只靠提示词里的 {{max_rounds}}。

## 三、工具说明怎么维护

| 关注点 | 位置 |
| --- | --- |
| 给模型看的用法说明（用途/必填/返回/耗时/依赖） | `backend/app/agent/tool_docs.py` 的 `TOOL_DOCS`（**写死**） |
| 给 function calling 的机器契约（name/params/required） | `tools` 表，页面可改；由 `build_tool_schema()` 下发 |
| 提示词里引用工具清单 | 只写 `{{tools}}`，不要内联 |

三个约定：

1. **新增工具必须补 `TOOL_DOCS`**。漏补不会静默：`render_tools_text` 会在清单里明确写出
   "以下工具没有登记说明，请补上：xxx"。
2. **只注入该 Agent 勾选的工具**（按 `tool_ids` 顺序），不是把全部工具塞进每个提示词。
3. 改完 `tool_docs.py` 要**重启后端**（当前无热重载启动），然后用下面的脚本确认：

```bash
python scripts/preview_agent_prompt.py 36
```

它会打印最终装配出来的 system prompt，并检查 `{{tools}}` / `{{max_rounds}}` 是否都已被替换。
